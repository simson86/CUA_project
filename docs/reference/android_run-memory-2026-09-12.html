왜 SQLite인가 — 성능이 아니라 안전 때문

기억 수백 건이면 JSON 파일로도 충분히 빠르다. SQLite를 고른 이유는 둘이다.

  • 원자적 쓰기 — 접근성 서비스는 시스템이 임의로 종료한다. JSON을 쓰는 도중 죽으면 사용자가 몇 주간 쌓은 기억이 통째로 깨진다.
  • 동시 접근 — 접근성 서비스(읽기·리플렉터)와 목록 UI(사람의 편집)가 같은 데이터를 만진다.

둘 다 자동 쓰기가 시작될 때 생기는 문제다. 그래서 사람만 편집하는 1단계는 JSON으로 시작해도 안전하다(부록 D). FTS5와 CASCADE는 덤이다.

버린 선택지 — 기준은 용량이 아니라 수정 가능성

모델 가중치✗파인튜닝 미개방. 열려도 틀린 지식을 빼는 unlearning은 미해결
서버 세션✗우리가 편집할 수 없다 = 틀린 기억을 못 지운다. 비용도 폭발
호스팅 메모리 API보류기술적으로 가능하나 프라이버시·적합성 문제(부록 E)

우리 환경은 앱 업데이트로 UI가 계속 바뀐다. 빠른 무효화가 필수인 문제에서 수정 불가능한 저장소는 최악이다.

분류는 저장 위치를 나누지 않는다

APP_FACT·PITFALL·RECIPE 세 종류는 전부 같은 memory 테이블에 산다. 분류가 나누는 것은 저장 위치가 아니라 검색 키와 주입 경로다(⑤·⑥). 분류 체계 자체는 부록 C.

리플렉터가 받는 것

입력왜 필요한가
run 1행목표가 뭐였고 성공했는지
episode 전체턴별로 무슨 일이 있었나 — 주 재료

세 번째가 빠지면 리플렉터가 이미 아는 것을 매번 새로 발견한다.

출력은 자유 문장이 아니라 템플릿이다

이것이 ③의 절반을 구조적으로 해결한다.

리플렉터 출력칸을 채운다 — 문장을 쓰지 않는다
{
  "kind":        "APP_FACT",
  "trigger":     "trash icon tap",              // 무엇을 하면
  "consequence": "a second confirmation dialog appears",  // 무엇이 일어나나
  "pkg":         "com.sec.android.gallery3d",
  "keywords":    "delete,remove,trash,휴지통,삭제,지우",   // 동의어 포함
  "source_turn": 7
}

주입 시점에 문장으로 조립된다 — "In Samsung Gallery, tapping the trash icon opens a second confirmation dialog."

왜 템플릿인가

trigger → consequence 두 칸뿐이면 잔액이나 이름을 넣을 자리 자체가 없다. 문장을 검사해서 걸러내는 것보다 새어나갈 칸을 없애는 것이 훨씬 강하다(③).

실패만 배우는 게 아니다

성공은 오히려 승격이 절반값이다 — "실제로 통했다"는 직접 증거이기 때문이다(⑦).

신호의 성질주로 낳는 것
실패뾰족함 — 어디를 볼지 알려줌PITFALL · APP_FACT (함정)
성공뭉툭함 — 무엇이 유용했는지 특정하기 어려움RECIPE · APP_FACT (경로)

초기 단계가 실패 쪽에 기울어 보이는 것은 성공을 무시해서가 아니라, 성공이 주로 낳는 RECIPE의 측정 효과가 약하기 때문이다(+1.4점 대 +24.4점, ⑨).

어려운 것은 뽑는 게 아니라 안 뽑는 것

배운 게 없으면 0건을 내는 것이 정답이다. 억지로 뽑은 후보가 곧 노이즈가 되고, 그 노이즈는 reconciliation 대조 비용까지 늘린다. 리플렉터 프롬프트의 가장 중요한 부분이 여기다.

"이 사용자는 새벽에 쇼핑앱을 자주 연다"는 화면 내용이 아니지만 행태 프로파일링이다. 역시 금지다. 다만 선호는 출처에 따라 갈린다.

같은 내용, 다른 출처저장

집행 — 네 겹, 등급이 다르다

등급누가무엇을 막나성질
A 구조적템플릿두 칸뿐이라 값을 넣을 자리가 없음어길 수 없음

B층의 "원문 대조"가 핵심이다. 후보의 토큰이 그 실행의 화면 텍스트에 그대로 있으면 의심한다 — 구조는 우리가 요약한 말이라 원문과 다르고, 내용은 화면에서 복사돼 와서 원문과 같다.

완벽할 필요가 없는 이유

비용이 심하게 비대칭이다 — 오탐(구조인데 버림)은 기억 하나를 잃을 뿐이고, 미탐(내용인데 통과)은 개인정보를 영구 저장한다. 그리고 결정적으로 기억은 재관측이 가능하다 — 오늘 버려도 같은 앱을 다음에 쓰면 다시 뽑는다. 버리는 비용이 거의 0이므로 애매하면 무조건 버린다.

D층이 실제로 작동하는 이유

새 기억은 PENDING에서 시작해 모델에게 가지 않는다. ⑦의 2회 승격 규칙이 검역 기간을 겸한다 — 사람이 목록에서 보고 지울 시간이 생긴다.

언제 쓸까

기억을 언제 DB에 쓰는가.

실행이 끝난 뒤 한 번, 루프 밖에서. 실행 중에는 episode에 기록만 쌓는다.

기록과 학습은 다르다

기록은 실행 중, 학습은 실행 후. 매 턴 episode에 행을 추가하는 것은 학습이 아니다 — 무슨 일이 있었는지 적어두는 것뿐이다.

왜 루프 안에서 쓰면 안 되나

  1. 결과를 모르는 시점의 추측이 저장된다 — 5턴째에 "이 앱은 이렇구나" 싶어도 그 실행이 결국 실패하면 틀린 교훈이다
  2. 매 턴 지연이 는다 — 리플렉터는 LLM 호출이다
  3. 실패한 실행의 잘못된 중간 판단이 남는다

reconciliation — 쓰기의 필수 부품

같은 사실인데 리플렉터가 매번 다른 문장을 쓴다. 문자열 비교로는 영원히 같은 기억으로 묶이지 않고, 그러면 ⑦의 카운터가 죽는다.

그래서 후보와 기존 기억을 함께 모델에 넘겨 판정을 받는다:

판정처리
ADD새 행 · PENDING · score 1
NOOP기존 행 score + 1 — 여기서 승격이 일어난다
UPDATE기존을 RETIRED로, superseded_by에 새 id
DELETE기존을 RETIRED로

3단계로 미룰 수 없다

reconciliation은 정리 기능이 아니라 승격 카운터의 전제다. 이것 없이 자동 추출을 켜면 같은 사실이 score 1짜리 중복으로 무한히 쌓이고 아무것도 승격되지 않는다.

개정 3 — 비대칭을 고쳤다

초판은 깎는 경로만 있고 올리는 경로가 없었다. 그러면 실전에서 50번 쓰여 50번 성공한 기억과 방금 겨우 승격된 기억의 score가 같아 랭킹에서 구분되지 않는다. 상한 4를 두어 매일 쓰는 앱의 기억이 무한정 부풀지 않게 한다.

"2회"는 반드시 실행 간이다

리플렉터는 실행당 한 번만 돌므로 한 실행은 최대 +1만 기여한다. 한 실행 안의 반복 실패는 '모델이 루프에 빠진 것'이지 앱의 성질이 아니다.

4번이 왜 차별점인가

다른 시스템은 "이 사실이 언제 무효가 됐나"를 LLM 추론이나 시간 규칙으로 힘겹게 판정한다. 우리는 longVersionCode가 바뀌는 것을 결정론적으로 안다. UI 변경이 staleness의 주원인인데 그 사건을 직접 관측하는 것이고, 폰 안에 있어야만 가능하다.

다만 즉시 강등하지는 않는다 — 마이너 업데이트는 대개 UI를 안 바꾸는데 매번 전부 날리게 된다. ACTIVE를 유지하되 version_match를 감점하고 목록 UI에 "갤러리가 업데이트됐습니다 · 확인 필요 3건" 배지를 띄운다.

그런데 실질적 무효화는 여기서 일어난다. ⑦의 카운터는 무작위 노이즈만 막고, 모델의 체계적 편향은 사람만 막는다 — 같은 모델이 같은 편향을 가지면 서로 다른 실행에서도 똑같이 틀리고, 카운터는 그걸 오히려 승격시킨다. 그래서 목록 UI는 편의 기능이 아니라 아키텍처의 일부다.

왜 창구 2가 반드시 필요한가

"음악은 유튜브 뮤직으로 열어"는 로그에 성공으로 찍힌다. 작업이 성공해도 사용자는 불만족일 수 있고, 로그는 그 차이를 원리적으로 볼 수 없다. 리플렉터만으로는 이 종류의 기억이 영원히 생기지 않는다.

용어 — procedural을 설계 어휘로 쓰지 않는다

개정 4 — 초안의 서술이 오해를 불렀다

초안은 "절차 기억은 DB 밖"이라고 썼다. 인지심리학의 엄밀한 정의(말로 옮길 수 없는 수행 능력)를 적용하면 맞는 말이지만, 우리가 만들고 있는 것을 안 만든다고 말한 꼴이었다.

AI 에이전트 실무 문헌(LangChain·Mem0·IBM 등)에서 procedural memory는 "성공했던 행동 궤적이나 루틴을 저장해 매번 재추론하지 않게 하는 것"을 뜻하고, 그것이 정확히 우리 RECIPE다. 안 만드는 게 아니라 4단계로 미뤄둔 것이다.

살아남는 쟁점은 정의가 아니라 인코딩이다.

궤적을 이렇게 저장하면
click(412,830) → click(500,900)✗ 매크로. UI 한 번 바뀌면 전부 깨짐
POST /api/cart → POST /api/checkout✓ 식별자가 안정적 — 웹·API 에이전트는 이게 됨
"YouTube Music을 열고 → 검색 탭 → 곡명 입력"✓ 모델이 매 단계 화면을 봄 ← 우리 방식

브라우저·API 에이전트가 궤적 재생을 안전하게 하는 건 다음에도 그 식별자가 그대로 있기 때문이다. 우리는 픽셀을 누르는 GUI 에이전트라 그 전제가 없다 — AppAgent가 좌표를 저장했다가 앱 업데이트에 전부 무효화된 것이 그 사례다.

혼란을 줄이기 위해 이 문서는 procedural이라는 단어를 쓰지 않고 RECIPE로만 부른다. 참고로 CoALA는 엄밀한 정의를 따라 procedural = LLM 가중치 + 에이전트 코드로 쓴다 — 같은 단어가 문헌마다 다른 것을 가리킨다.

개정 4 — RECIPE를 4단계에 둔 이유 재정리

"근거가 약해서"가 아니다 — ⑨에서 정정했듯 그 효과를 재는 숫자가 아직 없을 뿐이다. 뒤로 둔 실제 이유는 셋이다: ⑴ 정체성 경계(매크로)에 가장 가깝고 ⑵ precondition 검증이 선행돼야 하고 ⑶ APP_FACT가 먼저 효과가 크다.

턴 수 관점에서 보면 4단계가 너무 뒤일 수 있다 — 재검토 여지를 남긴다(부록 F).

기각 · 우리 구조와 충돌

system prompt를 자가 수정하게 한다 (LangChain 방식)

LangChain 계열은 procedural memory를 에이전트의 프롬프트로 구현하고, 피드백을 반영해 스스로 고쳐 쓰게 한다. 대화형 어시스턴트에는 성립한다.

우리는 안 된다 — ⑥의 네 이유 때문이다. 특히 안전 규칙이 system_prompt에 있다. 거기를 학습 대상으로 열면 ③의 규칙 A가 무너진다.

유예 · 기각 아님

온디바이스 임베딩

초판은 "임베딩 모델 필수"를 기각 사유로 적었으나 부정확했다 — 그것은 위 라이브러리들이 임베딩 서버와 벡터 DB를 요구한다는 뜻이었지 폰에서 불가능하다는 뜻이 아니다. ONNX·MediaPipe로 소형 모델을 돌릴 수 있고, 수백 건이면 벡터 DB 없이 전수 코사인으로 충분하다.

그럼에도 4단계로 미룬다: 필요한 곳이 PITFALL 하나뿐이고(⑤), 더 싼 대책 둘이 먼저 있고, APP_FACT에는 오히려 해롭다. 순서의 문제다.

기각 · 도메인이 얕다

그래프 검색을 도입한다

HumemAI·Zep의 그래프는 다중 홉을 위한 것이다(사람 → 소속 → 제품). 우리 조회는 1홉이다 — 패키지 → 그 앱의 사실. 타고 갈 간선이 없다. 필요한 관계 둘은 컬럼으로 충분하다 — superseded_by와 scope. 관계를 기록하는 것과 그래프를 순회하는 것은 다른 요구다.

보류 · 조건부 재검토

호스팅 메모리 API를 REST로 붙인다

기술적으로는 가능하다 — OkHttp만 있으면 되고 앱은 이미 Gemini에 REST를 쏜다. 초판의 "네트워크에 묶인다"는 반론은 틀렸다: 폰은 이미 매 턴 구글 서버를 호출하며, 끊기로 한 것은 케이블이지 네트워크가 아니다.

기각 사유는 셋이다. ① 맞지 않는다 — 우리 읽기는 패키지명 사전 조회지 의미 검색이 아니다. ② 어려운 절반이 남는다 — 버전 기반 무효화는 외주 불가. ③ 프라이버시 — ③이 막으려는 바로 그것이 제3자에 지속되는 프로필로 쌓인다.

재검토 조건 — 기기가 여러 대가 될 때 · 기억이 수천 건이 될 때 · 팀 단위 감사가 필요할 때. ⑥의 Gateway가 DAO 경계를 쥐고 있어 갈아끼울 수 있다.
