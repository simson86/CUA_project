# 3.5-flash vs 3.6-flash 토큰 사용량 (실측)

측정일 2026-08-11. 방식: **1턴 대조 실험** — 같은 스크린샷·같은 목표·같은 사고수준(`low`)을
두 모델에 번갈아 보내고 응답의 `usage` 를 비교. REST `/v1beta/interactions` 직접 호출
(`CuClient.cuCall` 과 동일한 본문). n=8 / 모델.

목표 문장: `설정 앱을 열어서 와이파이를 켜줘` — 두 모델 모두 8회 전부 `list_apps` 를 골랐다
(판단이 갈리지 않아 토큰 비교의 조건이 맞았다).

---

## §0 결론

| | 3.5-flash | 3.6-flash | 판정 |
|---|---|---|---|
| `total_input_tokens` | **1573** | **1573** | 완전 동일 |
| `total_output_tokens` | 23~28 | 23~27 | 동일 |
| `total_thought_tokens` 평균 | 58.6 | 63.4 | **구분 불가 (노이즈)** |
| `total_tokens` 평균 | **1657** | **1661** | 차이 0.2% — 무의미 |
| 응답 지연 평균 | 9.4초 | **8.2초** | 3.6 이 빠름 (8쌍 중 7쌍) |

**턴당 토큰은 사실상 같다.** 모델을 바꿔서 토큰을 아끼려는 계산은 성립하지 않는다.

**멀티턴(§1.5, n=5)도 같은 결론이다** — 중앙값 3턴 / 약 12,900 토큰으로 둘이 겹친다.
평균만 보면 3.6 이 절반으로 보이지만 그건 3.5 의 이상치 한 판(7턴, 49,780) 때문이다.
실제로 갈릴 여지가 있는 건 **잘 풀릴 때의 비용이 아니라 길을 잃는 빈도**이고,
그건 n=5 로는 판정할 수 없다.

> ★ 처음 n=2 로 봤을 때는 3.6 의 사고 토큰이 3.5 의 절반(47·50 vs 129·73)으로 보였다.
> 표본을 8로 늘리니 **뒤집혔다**(3.5 가 오히려 조금 낮음). 사고 토큰은 같은 모델·같은
> 입력에서도 28~129 로 흔들린다 — **n=2 로 판단하면 안 된다.**

## §1.5 멀티턴 실측 (실기기, n=5/모델)

2026-08-11. 소켓 `BENCH` 로 자동 실행. 매 판 전에 홈으로 되돌림. 모델 번갈아.
목표: `설정 앱을 열어서 휴대전화 정보에 들어가 안드로이드 버전을 확인해줘` (읽기 전용).
**10판 전부 완료(실패 0).**

| # | 3.5 턴 | 3.5 토큰 | 3.5 초 | 3.6 턴 | 3.6 토큰 | 3.6 초 |
|---|---|---|---|---|---|---|
| 1 | **7** | **49,780** | 111.1 | 3 | 12,824 | 29.3 |
| 2 | 3 | 12,915 | 36.7 | 3 | 12,887 | 74.5 |
| 3 | 3 | 12,955 | 37.6 | 3 | 12,945 | 47.3 |
| 4 | 3 | 12,840 | 34.1 | 3 | 12,843 | 30.9 |
| 5 | 3 | 12,877 | 34.6 | **2** | **4,572** | 20.6 |
| **중앙값** | **3** | **12,915** | 36.7 | **3** | **12,843** | 30.9 |
| 평균 | 3.8 | 20,273 | 50.8 | 2.8 | 11,214 | 40.5 |

### 결론: 보통은 똑같다. 갈리는 건 **사고 실패의 빈도**다

- **중앙값이 사실상 동일하다** — 둘 다 3턴, 약 12,900 토큰. 잘 풀릴 때는 구분이 안 된다.
- **평균이 갈리는 건 이상치 하나 때문이다.** 3.5 가 1회차에 폰 정보 화면을 못 찾아
  `open_app` ↔ `go_back` 을 반복하며 7턴을 썼다(**4배 비용**). 3.6 의 최악은 3턴이었다.
- 반대로 3.6 은 5회차에 2턴으로 끝냈다(운 좋은 지름길).
- **n=5 로는 "3.6 이 더 안정적이다"라고 말할 수 없다.** 방향만 시사한다.

### ★ 소표본이 두 번 연속 뒤집혔다 — 이 프로젝트의 교훈

| 언제 | 그때의 결론 | 표본 늘린 뒤 |
|---|---|---|
| 1턴 n=2 | "3.6 이 사고 토큰 절반" | **틀림** — 노이즈, 오히려 3.5 가 조금 낮음 |
| 멀티턴 n=1 | "3.6 이 3.9배 싸다" | **틀림** — 그 1판이 3.5 의 이상치였음 |

두 번 다 **첫 관측이 극적일수록 이상치일 가능성이 높다**는 쪽으로 움직였다.
이 저장소에서 모델 비교를 할 때는 **n≥5, 중앙값과 원자료를 함께** 보고,
평균만으로 판단하지 말 것.

### 이 작업은 너무 쉬웠다

10판 중 9판이 3턴에 끝났다 — 두 모델을 가를 만큼 어려운 과제가 아니다.
차이를 보려면 **여러 화면을 거치고 스크롤·검색이 섞인 작업**으로 다시 재야 한다.

### 시간은 결론 못 냄

3.5 중앙값 36.7초 / 3.6 중앙값 30.9초지만, 3.6 이 74.5초까지 튄 판이 있다.
1턴 실험에서 본 "3.6 이 빠름"과 방향은 같으나 편차가 커서 단정할 수 없다.

## §1.6 ★ 턴 단위 비교 — 여기서 진짜 차이가 나온다

총 토큰은 턴 수에 지배당해 모델 자체의 성질이 묻힌다. **요청 #k 끼리** 비교하면
히스토리 길이가 같은 조건에서 볼 수 있다. 위 4라운드 로그를 요청 단위로 분해했다
(7턴 이상치 판은 로그가 덮여 빠짐 — 정상 3턴 실행 4라운드).

턴이 올라갈수록 입력이 커지는 건 서버 관리 히스토리가 쌓이기 때문이다
(1580 → 약 4965 → 약 6110).

| 요청 | 항목 | 3.5 | 3.6 | 차이 |
|---|---|---|---|---|
| #1 | input | **1580** | **1580** | 4라운드 전부 정확히 일치 |
| #1 | thought | 57 | 67 | +10 |
| #2 | input | 4965 | 4969 † | ±4 |
| #2 | thought | 22 | 33 | +10 |
| #3 | input | 6110 | 6106 | −4 |
| #3 | thought | 86 | 92 | +7 |
| **#3** | **cached** | **3088 (4판 중 3판)** | **0 (3판 전부)** | ★ |

† 3.6 의 4회차는 액션 순서가 달라(아래) 히스토리가 짧다. 같은 순서인 3판만 평균.

### (1) 턴당 입력 토큰은 **완전히 같다**

요청 #1 은 4라운드 8회 모두 정확히 1580. #2·#3 도 오차 ±4. 히스토리가 어느 깊이든
같다 — §0 의 1턴 결론이 모든 턴 깊이에서 유지된다. **모델을 바꿔 토큰을 아낀다는
계산은 어느 층위에서도 성립하지 않는다.**

### (2) ★ 캐시는 3.5 만 걸린다 — 유일하게 실재하는 턴당 차이

요청 #3 은 두 모델의 입력이 약 6110 으로 같은데, **3.5 는 약 3,088 토큰이 캐시로 잡히고
(4판 중 3판) 3.6 은 0 이다(3판 전부).** 앞서 총량으로 볼 때는 "번갈아 돌려서 캐시
연속성이 끊긴 것 아니냐"는 반론이 가능했지만, **같은 요청 번호·같은 입력 크기에서
한쪽만 0** 이므로 그 설명은 안 통한다.

캐시는 #1·#2 에선 양쪽 다 0 이고 #3 에서 처음 걸린다 — 암시적 캐시가 걸리려면 접두
길이가 일정 이상이어야 하는 것으로 보인다.

**의미:** 캐시된 입력이 더 싸게 과금된다면, **총 토큰이 같아도 3.5 가 저렴하다.**
다만 3.6 이 캐시를 아직 지원하지 않는 것인지, 조건이 다른 것인지는 확인 안 됨.

### (3) 3.6 이 매 요청 사고 토큰을 조금 더 쓴다

#1·#2·#3 모두 3.6 이 높다(+10, +10, +7). §0 의 1턴 측정(3.5 58.6 / 3.6 63.4)과도
방향이 같다. **방향은 4/4 로 일관되지만 크기가 10 토큰 수준**이라 6,000 토큰짜리
요청에서는 무시해도 되는 양이다.

### (4) ★ 3.6 은 `list_apps` 를 건너뛴다 — 싸지만 지시 위반

4회차에서 3.6 이 2턴에 끝낸 것이 §1.5 에서 "운 좋은 지름길"로 보였는데, 로그를 보면
그게 아니다:

```
3.5 4회차: [턴 1] list_apps → [턴 2] open_app(com.android.settings) → 완료
3.6 4회차: [턴 1] open_app(com.android.settings) → 완료          ← list_apps 건너뜀
```

`system_prompt` 는 **"앱에 가려면 `list_apps` 를 먼저 부르라"** 고 명시한다. 3.6 은
그걸 건너뛰고 패키지명을 추측해서 넣었고, `com.android.settings` 가 널리 알려진
이름이라 우연히 맞았다. 낯선 한국어 앱("배민")이었으면 실패했을 것이다.

→ **싼 실행이 더 나은 실행이 아니다.** 이 저장소의 「완주 ≠ 정답」 함정이 비용 측정에서
드러난 형태다. 모델 비교에서 토큰만 보면 **지시를 안 지키는 쪽이 이긴 것처럼 보인다.**

## §2 ★ 1턴 측정이 **답하지 못했던** 것 (이제 §1.5·§1.6 이 일부 답함)

**턴당 토큰은 총비용의 결정 요인이 아니다.** 실행 한 판의 비용은

```
비용 ≈ (턴당 토큰) × (턴 수) − (캐시로 깎이는 몫)
```

이고, 이 실험은 **첫 항만** 쟀다. 나머지 둘은 1턴 실험으로 잴 수 없다:

1. **턴 수** — 여기서 완전히 빠져 있다. 턴당 토큰이 같아도 3.6 이 한 작업을 8턴에 끝내고
   3.5 가 12턴 쓴다면 비용은 1.5배 차이다. **이쪽이 훨씬 크게 작용한다.**
2. **캐시** — 8회 전부 `total_cached_tokens = 0` 이었다. 전부 `previous_interaction_id`
   없는 첫 턴이라 캐시가 걸릴 수가 없다. 실제 멀티턴 실행에서는 시스템 프롬프트가
   캐시된다(`CLAUDE.md` 기록: 실측 6799). 모델별 캐시 적중률이 다를 여지가 있다.

→ 그래서 **앱에 턴별 토큰 로깅을 넣었다**(§3). 실기기 멀티턴 실행으로만 답이 나온다.

## §3 실제 멀티턴 측정 방법 (앱)

`runAgent` 가 요청마다 아래를 남긴다. `run_history.txt` 와 앱 로그 화면에 찍힌다.

```
[설정] model=gemini-3.6-flash thinking=low maxTurns=20
[토큰] usage 원본: {"total_tokens":…, …}          ← 첫 요청에만. 항목 누락 확인용
[토큰] #1 total_tokens=1725 … | 누적 total_tokens=1725 …
[토큰] #2 …                  | 누적 …
```

★ **마지막 `[토큰]` 줄의 `누적` 이 그 실행의 총량이다.** 완료·중단·거부·최대턴 어느 쪽으로
끝나도 마지막 줄에 남는다(종료 지점마다 합계를 심으면 언젠가 하나를 빠뜨린다).

### 공정하게 재려면

이 저장소의 벤치 함정 기록과 같은 것들이 그대로 적용된다:

| 함정 | 대응 |
|---|---|
| **상태 이월** — 1회차가 폰을 다른 화면에 두고 끝나면 2회차의 출발점이 달라진다 | 매 실행 전 홈으로 되돌린다. 앱도 최근목록에서 정리 |
| **턴 수가 지배** — 총 토큰만 보면 안 된다 | `[완료] Done turn=n` 의 턴 수를 함께 기록 |
| **완주 ≠ 정답** — 적은 턴에 끝난 게 실패라서일 수 있다 | 실제로 작업이 됐는지 눈으로 확인. 실패한 실행은 표에서 뺀다 |
| **n=2 는 결론이 아니다** | §0 경고 참조. 최소 5회, 모델을 번갈아 |
| **지연은 상대적** — 세션·시간대에 따라 절대값이 크게 변한다 | 같은 세션 안에서 번갈아 돌린 쌍끼리만 비교 |
| **토큰 ≠ 비용** — 모델별 단가가 다를 수 있다 | 결론을 낼 땐 단가표를 곱한다 |

### 권장 절차

1. 폰을 홈으로. 같은 목표 문장을 정한다(여러 턴 걸리는 것으로).
2. 모델만 바꿔 가며 번갈아 5회씩 — 3.5, 3.6, 3.5, 3.6 …
3. 매 실행마다 `[완료]` 의 **턴 수**, 마지막 `[토큰]` 줄의 **누적**, 작업 **성공 여부**를 적는다.
4. 실패한 실행은 빼고 평균.

## §3.5 벤치를 돌리다 잡힌 앱 버그 2건 (2026-08-11)

멀티턴 벤치를 처음 돌리자마자 두 개가 나왔다. 손으로 몇 판 돌려서는 안 보이던 것들이다.

### (1) 스크린샷 실패가 엉뚱한 곳에서 죽었다 — **수정함**

증상: 12턴째에 실행이 `오류: length=0; index=16` 로 끝났다. 이 메시지만 보고는
원인을 알 방법이 없다.

원인: `capturePngBlocking` 의 `onFailure` 가 로그만 남기고 **빈 배열을 정상 반환**했다.
그 빈 배열이 `pngSize` 까지 흘러가 `png[16]` 에서 터진 것 — 즉 실패 지점과 폭발 지점이
달랐다. `takeScreenshot` 은 **호출 간격 제한(대략 1초)** 이 있어 연속 호출이 거절되는데,
이건 기다리면 풀리는 실패라 재시도로 넘길 수 있는 것이었다.

수정: 실패하면 1.1초 간격으로 **3회 재시도**, 그래도 안 되면
`스크린샷 실패 3회 (code=N)` 로 **그 자리에서 예외**를 던진다. 콜백이 영영 안 오는
경우를 위해 `latch.await` 에 10초 상한도 걸었다.

> 교훈: 빈 값을 정상값처럼 돌려주면, 진짜 원인에서 멀리 떨어진 곳에서 이해할 수 없는
> 메시지로 죽는다. 실패는 실패한 자리에서 말해야 한다.

### (2) ★ 에이전트가 **우리 앱의 '중단' 버튼을 누를 수 있다** — 미수정

증상: 3.6 실행이 1턴 만에 `[중단] 사용자 중단` 으로 끝났다. 아무도 버튼을 누르지 않았다.

`cancelled` 를 true 로 만드는 곳은 `MainActivity` 의 중단 버튼 **하나뿐**이다
(`requestCancel()`). 즉 **누군가 그 버튼을 눌렀다** — 그 직전 실행에서 모델이 길을 잃고
`go_back` / `open_app` 을 반복하다 우리 앱 화면으로 나왔고, 거기서 탭이 우리 UI에
떨어진 것으로 보인다. 재현은 아직 1회.

이건 벤치 도구 문제가 아니라 **설계 구멍**이다. 에이전트가 조작하는 화면에 우리 자신의
제어판이 있으면, 에이전트가 자기 자신을 멈추거나(중단) 설정을 바꾸거나(모델 드롭다운)
다시 실행시킬 수도 있다.

생각해 볼 대응:
- 실행 중에는 `MainActivity` 의 컨트롤을 비활성화한다(이미 실행/마이크는 잠근다 —
  **중단 버튼은 일부러 살아 있어야 하므로** 이게 완전한 답은 아니다).
- 실행 중 우리 앱이 포그라운드로 나오면 홈으로 밀어낸다.
- 근본적으로는 `⬜ 자체 안전 게이트`(CLAUDE.md) 쪽 문제 — 포그라운드 패키지가 우리
  자신이면 액션을 막는 규칙.

## §4 재현용 스크립트

1턴 대조 실험 스크립트는 스크래치패드 일회용으로 만들었고 저장소에 두지 않았다.
다시 필요하면: `adb exec-out screencap -p` 로 PNG 한 장 → `CuClient.cuCall` 과 같은 본문으로
모델만 바꿔 번갈아 호출 → `usage` 출력. 사고수준·시스템 프롬프트를 앱과 똑같이 맞춰야
숫자가 대표성을 갖는다.
