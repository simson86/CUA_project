# 기억 종류 체계 재설계 — `APP_FACT` · `RECIPE` 둘로 (2026-09-21)

> 판단 ② 배치 1·2 에서 관측된 고장 둘을 계기로, 종류 체계를 **검색 키 기준**으로 다시 세운다.
> 이 문서는 **설계 기록**이다. 현재 구현 상태는 `MEMORY.md` 를 본다.
>
> 관련: `MEMORY.md` 의 「종류 체계 다시 보기」(2026-09-16) · 「배치 1 결과」 · 「배치 2 결과」

---

## 0. 한 줄 요약

`PITFALL` 을 없애 `APP_FACT` 에 흡수하고, 경로·절차 지식을 `RECIPE`(목표 + 패키지)로 옮긴다.
종류는 **둘**이 되고, 리플렉터 프롬프트가 이미 선언한 두 갈래와 **1:1** 로 맞는다.

```
프롬프트가 "쓸 가치 있다"고 한 것        저장 종류      검색 키
──────────────────────────────────────────────────────────────────
(b) SURPRISE — 이 앱은 네 예상과 다르다  →  APP_FACT    패키지
(a) DIRECTION — 어디를 눌러 어디로 간다  →  RECIPE      목표 + 패키지 (+ 폴백)
```

## 1. 왜 — 관측된 고장 둘

배치 1·2(24회 실행, 기억 9건)에서 나온 것이다. 추측이 아니다.

### 고장 ① 틀린 기억이 **관계 없는 과제의 성공으로** 상한 점수를 얻었다

```
APP_FACT · ACTIVE · 점수 4(상한)
Searching for a teacher's course reviews → ... '수강평' tab ..., which supports
sorting by '최신순' (Newest).
주입 6회 · 1개 실행(성공 1)
```

마지막 절은 **사실이 아니다** — `최신순` 을 고르면 508건이 0건이 된다(사람이 폰에서 확인).
그런데 이 기억이 주입된 유일한 실행은 **M3-B(목표 대학, 7턴 성공)** 로 수강평과 아무
상관이 없다. 두 가지가 겹쳤다:

| | |
|---|---|
| `APP_FACT` 의 검색 키가 **패키지뿐** | 목표가 뭐든 그 앱이 뜨면 붙는다 |
| 카운터(Unit 6)가 **실행 결과로** 점수를 준다 | 기여했는지는 안 본다 |

```kotlin
when (outcome) {
    "success" -> { dao.raiseScore(ids); dao.activateProven(ids) }   // 주입된 전부 +1
    "fail"    -> { dao.lowerScore(ids); dao.retireExhausted(ids, now) }
}
```

→ **아무 과제나 성공하면 그 앱의 모든 `ACTIVE` 기억이 상을 받는다.**

「종류 체계 다시 보기」에서 *"검색 키가 헐겁다"* 의 대가를 **예산 낭비**로만 적었는데,
실제 대가는 **틀린 지식의 고착**이었다. 퇴출은 점수 ≤ 0 에서만 일어나므로 점수 4 짜리는
사실상 못 뺀다(`DELETE` 판정만이 유일한 길이고, 그건 점수와 무관하다).

### 고장 ② 예산을 목표와 무관한 기억이 먹는다

L3(하이라이트 가사 찾기)에 **시대별 차트 경로**가 주입됐다. 앱당 예산이 2줄인데 한 줄을
관계 없는 경로가 가져갔다.

> ⚠️ **`UPDATE` 가 점수를 리셋하는 문제(MEMORY.md 의 '고장 ②')는 이 문서의 범위가 아니다.**
> 그건 종류 체계와 무관한 `supersede()` 의 버그이고 따로 고친다(`F1`).

## 2. 분류 기준은 **내용이 아니라 검색 키** (명세서 부록 C)

이름이 내용을 가리키는 것처럼 보이지만 실제 정의는 이쪽이다.

| 종류 | 검색 키 | 주입 경로 |
|---|---|---|
| `APP_FACT` | 패키지명 | `appNote` · **매 턴** |
| `PITFALL` | 목표 키워드 | `taskNote` · 실행 내내 |
| `RECIPE` | **목표 + 패키지** | `taskNote` · precondition 확인 후 |

검색 키 × 내용의 2축으로 펴 보면 **이름이 셋인데 칸은 넷**이고, 한 칸에 이름이 없다:

| 검색 키 ＼ 내용 | 의미(사실) | 절차(경로) |
|---|---|---|
| **패키지** | `APP_FACT` | **← 이름 없음. 경로가 전부 여기 얹혀 있다** |
| **목표** | `PITFALL` | — |
| **목표 + 패키지** | — | `RECIPE` |

## 3. 실측 — 생성된 기억 9건의 실제 분포 ★

배치 1·2 에서 리플렉터가 만든 전부다.

| | 건수 | 비고 |
|---|---|---|
| **경로** (절차) | **8** | 메가선생님 경로 · 수강평 · 목표 대학 · 가사 v1/v2 · 차트 v1/v2/v3 |
| **오해할 요소** | 1 | 검색 아이콘·Enter 가 검색을 실행 못 함 |
| **앱의 사실·정보** | **0** | — |

**두 가지가 따라 나온다:**

1. **지금 `APP_FACT` 에 있는 것은 전부 잘못 분류된 `RECIPE` 다.** 값어치가 확인된 유일한
   것이 경로 지식인데(2차 −48.8%), 그게 패키지만 보는 칸에 앉아 있다.
2. **`PITFALL` 은 사실상 안 쓰인다.** 9건 중 1건이고, 그 1건마저 목표 키 때문에 죽어
   있었다(§5).

## 4. `PITFALL` 을 `APP_FACT` 에 흡수한다

### 4.1 둘은 같은 것을 가리킨다

리플렉터 프롬프트의 `SURPRISE` 정의:

```
(b) SURPRISE — where THIS app contradicts what you would expect of a typical Android
    app: a control that does not do what its label or shape suggests, a back gesture
    that exits instead of going back, a list that reorders between visits, a keypad
    whose digits move.
```

*"일반적인 앱 화면·아이콘과 달리 이 앱은 다르다"* 와 *"이 앱에서 오해할 만한 요소"* 는
같은 문장이다.

### 4.2 우리 유일한 실제 사례가 경계선 위에 있다 ★

```
"검색창 → 검색 아이콘이나 Enter 가 검색을 실행 못 할 수 있다"
```

| 질문 | 답 |
|---|---|
| 관례 위반인가 | ✅ 검색 아이콘은 보통 검색을 한다 |
| 화면에 안 보이는 성질인가 | ✅ 스크린샷으로는 먹통인지 알 수 없다 |

**둘 다다.** 경로가 아닌 유일한 한 건이 하필 경계선 위에 있다는 건 **그 경계가 실무에서
안 버틴다**는 신호다. 모델이 매번 찍어야 하고, 어느 쪽으로 찍든 **동작이 달라지지 않으면**
그 선택은 순수한 잡음이다.

### 4.3 `APP_FACT` 는 빈 통이 아니다 — 담을 것이 둘

님(사용자) 지적대로 이 범주는 필요하다. 다만 **경로가 아닌 것**만 담는다.

| 갈래 | 왜 값이 있나 | 예 |
|---|---|---|
| **관례 위반** | 모델의 **사전지식**이 틀리게 만든다 | 정렬 드롭다운이 검색을 리셋한다 · 검색 결과의 강사 사진은 클릭이 안 된다 |
| **화면에 안 보이는 성질** | **스크린샷**이 못 준다 | 이 탭 줄은 가로로 더 있다 · 이 버튼은 3초 뒤 반응한다 · 로그인해야 보인다 |

둘째 줄은 「종류 체계 다시 보기」가 적어 둔 *"`APP_FACT` 가 값어치를 가지려면 화면에 안
보이는 성질이어야 한다 — 시간 · 화면 밖 · 상태"* 의 자리다. 관례 위반은 아니지만 같은
이유로(모델이 이미 가진 것과 안 겹쳐서) 값이 있다.

M2 조사에서 찾은 함정 셋이 전부 여기 들어간다:

```
정렬 드롭다운 → 검색이 리셋된다           (관례 위반)
검색 결과의 강사 사진 → 클릭이 안 된다      (관례 위반)
프로필 탭 줄 → 가로로 밀어야 더 있다        (화면 밖)
```

### 4.4 그래도 둘로 나눌 근거가 있나 — 지금은 없다

나눌 이유로 떠오르는 것은 **예산 분리** 하나인데, 그 종류의 기억이 **9건 중 1건**이다.
예산을 다툰 적이 없으니 나눌 근거가 없다. 실제로 다투기 시작하면 그때 쪼개도 늦지 않다 —
**쪼개는 건 언제든 되지만, 안 쓰는 종류를 유지하는 비용은 매일 낸다**(주입·랭킹·
reconcile·목록 UI 에 분기가 하나씩 더 있다).

### 4.5 이름은 `APP_FACT` 가 남는다

*"이 목록은 아래로 더 있다"* 는 함정(pitfall)이 아니다. `APP_FACT` 가 중립적이고 둘 다
덮는다. 현재 `PITFALL` 행은 **1건(PENDING)** 뿐이라 옮기는 비용이 없다.

## 5. `PITFALL` 의 목표 키가 실제로 죽어 있었다 — 흡수의 부수 효과 ★

배치 1 에서 리플렉터가 만든 첫 `PITFALL`:

```
키워드: search bar, enter key, icon, click
```

매칭은 `goal.lowercase().contains(keyword)` 인데 우리 목표는 한국어다. **영원히 안 걸린다.**
주입이 없으니 `NOOP` 대상도 못 돼 승격 경로조차 없다.

원인은 모델이 아니라 **프롬프트였다: 매칭 방식을 설명한 적이 없다**(`text` 가 영문 권장이라
모델이 `keywords` 도 맞춘 것이 오히려 자연스럽다). 배치 1·2 사이에 규칙 7(예시 포함)을
넣어 고쳤으나 **아직 한 번도 걸려 본 적이 없다 — 검증 0회.**

**흡수하면 이 문제가 설계에서 사라진다.** *"이 앱은 이렇다"* 는 본질적으로 앱 속성이므로
패키지 키가 맞고, **목표 매칭에 의존하는 종류가 `RECIPE` 하나로 줄어든다.** 취약한
기계장치를 한 곳에 국한하는 것이 이 재설계의 숨은 이득이다.

---

## 6. `RECIPE` — 목표 + 패키지, 그리고 폴백

### 6.1 무엇이 해결되나

```
지금   : 메가스터디가 뜨면 → 수강평 경로도 목표대학 경로도 전부 붙는다
         → 목표 대학 과제가 성공하면 수강평 기억이 상을 받는다   (고장 ①)
RECIPE : 목표가 수강평에 관한 것일 때만 수강평 경로가 붙는다
         → 상을 받을 자리 자체가 없다
```

예산 낭비(고장 ②)도 같이 사라진다.

### 6.2 ⚠️ 위험 — 검증 0회인 매칭에 가치의 100% 를 건다

이 시스템에서 **효과가 확인된 유일한 것이 경로 지식**이다(2차 −48.8%). 새 구조에서 그게
전부 `RECIPE` 로 가고, `RECIPE` 는 목표 키워드 매칭에 의존한다. 그 매칭은 §5 에서 보듯
**한 번도 성공한 적이 없다.**

- 매칭이 **헐거우면** 지금과 같다(낭비).
- 매칭이 **빡빡하면 경로 기억이 통째로 안 뜬다** — 죽은 `PITFALL` 이 그 모습이었다.

### 6.3 ⚠️ 위험 — 목표가 다르면 공유 경로도 못 쓰나

M1(커리큘럼)과 M2(수강평)의 정답 경로는 **앞 두 걸음이 같다**(메뉴 → 메가선생님).
`RECIPE` 가 좁게 쓰이면 M1 의 기억이 M2 에 안 걸려 **전이가 끊긴다** — M2 를 과제 집합에
넣은 목적이 바로 그 전이 측정이었다.

**실제 데이터는 낙관적이다.** 리플렉터가 M1 만 보고 쓴 문장:

```
Accessing a teacher's profile or curriculum → The side menu contains '메가선생님' ...
                     ↑ "커리큘럼" 이 아니라 "프로필 또는 커리큘럼" — 스스로 일반화했다
```

키워드가 `강사, 선생님, 커리큘럼, 프로필` 로 나오면 M2 목표(`민동휘 **강사**의 최신 수강평`)에
걸린다. **다만 이건 운이다** — `커리큘럼` 만 적었으면 끊겼다.

### 6.4 대책 — 세 겹의 근사

경로는 원래 `공유 접두부 + 목표별 꼬리`다.

```
[공유]  강사 관련 정보 → 메뉴 → 메가선생님 → 과목 → 선생님 프로필
          키워드: 강사, 선생님, 강의, 커리큘럼, 수강평        ← 넓게
[꼬리1] 커리큘럼 → 프로필의 '커리큘럼' 탭      키워드: 커리큘럼   ← 좁게
[꼬리2] 수강평   → 프로필의 탭 줄을 가로로 밀어 '수강평'
                                              키워드: 수강평, 후기 ← 좁게
```

| 겹 | 무엇 | 성질 |
|---|---|---|
| ① 프롬프트 | *"재사용 가능한 접두부를 우선 쓰고, 목표별 꼬리는 따로 써라"* | 유도 |
| ② 프롬프트 | *"키워드는 그 목표류 전체를 덮게 넓게"*(규칙 7 의 연장) | 유도 |
| ③ **폴백** | 목표에 걸리는 게 없거나 예산이 남으면 **같은 앱의 상위 `RECIPE` 를 그냥 주입** | **구조** |

**③ 이 핵심이다.** ①② 는 모델 유도라 못 믿는다.

### 6.5 폴백 — 주입과 **가산을 분리**한다 ★★

```
목표가 걸린 RECIPE  →  주입 O · 점수 가산 O
폴백으로 들어간 것  →  주입 O · 점수 가산 X
APP_FACT            →  주입 O · 점수 가산 O   (패키지 키라 항상 해당한다)
```

이 한 줄이 두 가지를 동시에 한다:

- **전이가 안 끊긴다** — 키워드가 좁아도 M2 는 M1 의 경로를 폴백으로 받는다.
  최악이라도 **지금과 같다**(= 패키지만 보는 현재 동작). 퇴행이 없다.
- **고장 ① 이 사라진다** — 귀속을 못 하는 주입은 점수를 안 준다.

> 이것이 *"도움이 됐는지 판단할 수 있나"* 에 대한 이 설계의 답이다.
> **판단 못 하는 주입은 점수를 안 준다.** 판단 시도 자체를 안 한다.

### 6.6 랭킹의 `relevance` 가 처음으로 일한다

지금 식의 `relevance` 는 `APP_FACT` 면 무조건 1.0 이라 **사실상 죽은 항**이다
(MEMORY.md: *"명세의 자리만 채운 것"*). 새 구조에서 값이 생긴다:

| | `relevance` |
|---|---|
| 목표가 걸린 `RECIPE` | **1.0** |
| 폴백 `RECIPE` | **0.5** |
| `APP_FACT` | 1.0 (패키지 키라 항상 해당) |

즉 **예산이 모자라면 목표에 맞는 경로가 먼저 들어간다.** 지금은 그 구분이 아예 없어서
차트 경로가 가사 찾기에 들어갔다.

⚠️ 0.5 는 **근거 없는 값**이다. 가중치 넷이 그런 것과 같다(열린 결정 N1).

## 7. 정직한 한계

- **키워드 부분일치는 의미를 모른다.** *"이 경로의 앞 두 걸음이 지금 목표에도 해당한다"*
  를 판정할 수 없다. 폰에 임베딩이 없으므로 §6.4 의 세 겹 근사가 지금 할 수 있는 전부다.
- **부분일치는 원래 취약하다.** *"휴지통에 넣어줘"* 는 `삭제` 에 안 걸린다. 동의어를
  넣게 하는 것이 유일한 방어다.
- **이 문서가 안 고치는 것:**
  | | |
  |---|---|
  | `UPDATE` 가 점수를 리셋 (`supersede`) | `F1` 로 따로 |
  | `NOOP` 이 **문장 전체**를 승인 | 수강평 기억은 앞 절만 재관측됐는데 뒤 절까지 승인됐다. 절 단위 검증 수단이 없다 |
  | 이미 점수 4 인 틀린 기억 | `DELETE` 유도(`F3`) 가 있어야 빠진다 |
- **의미형 기억은 우리 측정에서 0/3 이다**(무신사 ±0.0% · 메타클럽은 **해로웠다** ·
  D 부정사실 0%). §4.3 이 *"`APP_FACT` 에도 담을 게 있다"* 고 말하지만, **그 값어치는
  아직 한 번도 측정된 적이 없다.** 시간·화면 밖·상태 갈래는 우리가 써 본 적조차 없다.

## 8. 이행 순서

한 번에 다 바꾸지 않는다. **`RECIPE` 가 안전하게 착지할 바닥을 먼저 깐다.**

| 단계 | 무엇 | 왜 이 순서 |
|---|---|---|
| **1** | `F1`(`supersede` 점수 승계) + 폴백형 귀속 게이트 | 값싸고 결정론적. **구조 변경 없이** 고장 ①②를 멈춘다 |
| **2** | `PITFALL` → `APP_FACT` 흡수 (패키지 키) | 님 안에서 가장 안전한 조각. **목표 매칭 의존을 줄이는** 방향이라 위험이 없다 |
| **3** | 배치 3~4 로 확인 | 경로 기억이 정상 주입되는지 · 점수가 제대로 붙는지 |
| **4** | `RECIPE` 도입 + 기존 8건 이관 | 폴백이 깔려 있으므로 매칭이 실패해도 퇴행하지 않는다 |

4 를 먼저 하면 *"효과가 확인된 유일한 자산을 미검증 매칭에 옮기는 일회성 도박"* 이 된다.

### 구현 규모 (4단계)

DB 마이그레이션은 **없다** — 스키마에 `steps`·`precondition`·`observedTurns` 가 이미 있고
`kind` 는 문자열이다.

| | |
|---|---|
| `KINDS` 에 `RECIPE` 추가 | 1줄 |
| DAO `activeRecipes` | ~10줄 |
| 게이트웨이: 목표를 캐시해 `readForApp` 에서 쓰기 | `appNote()` 가 목표를 안 받는다(`taskNote(goal)` 만 받음) → 실행 시작에 캐시 |
| 랭킹 `relevance` 분기 | ~5줄 |
| 리플렉터 프롬프트: 언제 `RECIPE` 인지 · 접두부/꼬리 분리 · 키워드 넓게 | 규칙 + 예시 |
| 기존 8건 이관 | **결정 필요** — 아래 |

> `precondition` 은 **구현하지 않는다.** 「경로 지식은 APP_FACT 인가 RECIPE 인가」의
> 결론대로 *"필요한 것은 장치가 아니라 검색 키"* 다 — 경로를 한 줄 서술로 넣어도

## 9. 열린 결정

| | 질문 | 메모 |
|---|---|---|
| **K1** | 기존 8건을 `RECIPE` 로 옮길 때 **점수를 살릴까 버릴까** | 살리면 틀린 수강평 기억(점수 4)도 따라온다. 버리면 검증된 경로가 재시작한다. `F1` 과 같은 성질의 문제 |
| **K2** | 예산 배분 | 지금 `APP_FACT 2 + PITFALL 2`. 실제 분포가 **경로 8 : 사실 1** 이라 `RECIPE 3 + APP_FACT 1` 이 맞아 보이지만, 배치 데이터를 더 보고 정한다 |
| **K3** | 폴백 `relevance` 0.5 | 근거 없는 값. 예산이 실제로 다투기 시작해야 튜닝할 재료가 생긴다 |
| **K4** | `APP_FACT` 의 값어치 | §7 — 의미형은 0/3 이었고 시간·화면밖·상태 갈래는 써 본 적이 없다. **별도 측정이 필요하다** |
| **K5** | 측정 경계 | 배치 1 = `PITFALL` 죽은 시스템, 배치 2~ = 산 시스템, 그리고 이 재설계가 또 경계를 만든다. **추이를 읽을 때 경계를 빼놓지 말 것** |
