# CU 에이전트 기억 설계 (`android/`)

폰 단독 온디바이스 경로에 **장기 기억**을 붙이는 구조. 에이전트가 남긴 일화에서 의미·절차
기억을 뽑아 기기 안 SQLite에 쌓고, 다음 실행에서 상황에 맞는 것만 예산 안에서 모델 입력에
얹는다.

이 문서는 **반드시 답해야 하는 아홉 개의 질문**으로 구성된다. 하나라도 비면 기억 시스템이
성립하지 않는다.

**상태: 설계안 · 미구현.** 선행 조건은 0단계 구조화 로깅이다.

```
[저장 전]  ① 어디에 둘까   ② 무엇을 뽑을까   ③ 무엇을 막을까
[저장]     ④ 언제 쓸까
[꺼내기]   ⑤ 어떻게 찾을까  ⑥ 어디에 붙일까
[관리]     ⑦ 강화와 소멸    ⑧ 사람의 개입
[검증]     ⑨ 효과가 있나
```

---

## §1 어디에 둘까

> **질문** — 기억이 물리적으로 어디에 사는가.
> **답** — 기기 안 SQLite 파일 하나(`memory.db`). 그 밖은 DB가 담을 수 없는 종류다.

먼저 전체 지형. "기억이라 할 만한 것"은 열 군데에 흩어져 있다.

| 저장소 | 실행 간 | 모델에 감 | 누가 쓰나 | 무엇 |
|---|---|---|---|---|
| 모델 가중치 | 영구 | *안에 있음* | 구글 | 체득된 감각 |
| 앱 소스코드 | ✓ | ✗ | 개발자 | 실행 능력 |
| `CuClient.kt:154` `system_prompt` | ✓ | ✓ 매 요청 | 개발자 | 항상 참인 규칙 |
| **`CuClient.kt:208` `taskNotes`** | ✓ | ✓ 조건부 | 개발자 → **앱** | 작업별 함정 |
| **`a11service.kt:241` `appNotes`** | ✓ | ✓ 조건부 | 개발자 → **앱** | 앱별 사실 |
| **`memory.db`** | ✓ | ✓ 조건부 | **앱 + 사람** | 일화 · 의미 · 절차 |
| `SharedPreferences` | ✓ | ✗ | 사용자 | 모델·사고수준·턴수 |
| `run_history.txt` | ✓ | ✗ | 앱 | 사람이 읽는 로그 |
| 실행 중 히스토리 | **✗ 소멸** | ✓ | 앱 | 단기 기억 |
| `CLAUDE.md`·`docs/` | ✓ | ✗ | 개발자 | 사람의 기억 |

**이 프로젝트가 하려는 일을 한 줄로** — 위 표에서 `taskNotes`·`appNotes` 두 줄의 "누가
쓰나"를 *개발자 → 앱*으로 바꾸는 것. 주입 경로도, 요청 형식도, 나머지 여덟 줄도 그대로다.

### 왜 SQLite인가 — 성능이 아니라 안전

수백 건이면 JSON으로도 충분히 빠르다. 이유는 둘이다.

- **원자적 쓰기** — 접근성 서비스는 시스템이 임의 종료한다. JSON을 쓰는 도중 죽으면 사용자가
  몇 주간 쌓은 기억이 통째로 깨진다.
- **동시 접근** — 접근성 서비스(읽기·리플렉터)와 목록 UI(사람의 편집)가 같은 데이터를 만진다.

둘 다 *자동 쓰기가 시작될 때* 생기는 문제다. 그래서 사람만 편집하는 1단계는 JSON으로 시작해도
안전하다(§부록 D). FTS5와 `CASCADE`는 덤이다.

### 버린 선택지 — 기준은 용량이 아니라 수정 가능성

| 후보 | | 탈락 이유 |
|---|---|---|
| 모델 가중치 | ✗ | 파인튜닝 미개방. 열려도 unlearning은 미해결 |
| 서버 세션 | ✗ | 우리가 편집 불가 = **틀린 기억을 못 지운다** |
| 호스팅 메모리 API | 보류 | 기술적으로 가능하나 프라이버시·적합성 (§부록 E) |
| **기기 안 SQLite** | ✓ | 읽고·고치고·지울 수 있는 유일한 층 |

우리 환경은 **앱 업데이트로 UI가 계속 바뀐다.** 빠른 무효화가 필수인 문제에서 수정 불가능한
저장소는 최악이다.

> **분류는 저장 위치를 나누지 않는다.** `APP_FACT`·`PITFALL`·`RECIPE`는 전부 같은 `memory`
> 테이블에 산다. 분류가 나누는 것은 *검색 키와 주입 경로*다(§5·§6).

## §2 무엇을 뽑을까

> **질문** — 20턴짜리 로그에서 무엇이 남을 가치가 있는가.
> **답** — 실행이 끝난 뒤 리플렉터(텍스트 전용 호출 1회)가 **정해진 칸을 채워** 후보를 낸다.
> 0건이 정상이다.

### 리플렉터가 받는 것

| 입력 | 왜 필요한가 |
|---|---|
| `run` 1행 | 목표가 뭐였고 성공했는지 |
| `episode` 전체 | 턴별로 무슨 일이 있었나 — 주 재료 |
| **그 실행에 주입됐던 기억** | 이미 아는 걸 또 제안하지 않도록 · 도움이 됐는지 판단하도록 |

세 번째가 빠지면 리플렉터가 **이미 아는 것을 매번 새로 발견한다.**

### 출력은 자유 문장이 아니라 템플릿

이것이 §3의 절반을 구조적으로 해결한다.

```json
{
  "kind":        "APP_FACT",
  "trigger":     "trash icon tap",
  "consequence": "a second confirmation dialog appears",
  "pkg":         "com.sec.android.gallery3d",
  "keywords":    "delete,remove,trash,휴지통,삭제,지우",
  "source_turn": 7
}
```

주입 시점에 문장으로 조립된다 — *"In Samsung Gallery, tapping the trash icon opens a second
confirmation dialog."*

**`trigger` → `consequence` 두 칸뿐이면 잔액이나 이름을 넣을 자리 자체가 없다.** 문장을
검사해서 걸러내는 것보다 *새어나갈 칸을 없애는 것*이 훨씬 강하다.

`RECIPE`는 칸이 다르다 — §부록 A 참조.

### 실패만 배우는 게 아니다

성공은 오히려 승격이 절반값이다("실제로 통했다"는 직접 증거).

| | 신호의 성질 | 주로 낳는 것 |
|---|---|---|
| **실패** | 뾰족함 — 어디를 볼지 알려줌 | `PITFALL`·`APP_FACT` (함정) |
| **성공** | 뭉툭함 — 무엇이 유용했는지 특정하기 어려움 | `RECIPE`·`APP_FACT` (경로) |

**어려운 것은 뽑는 게 아니라 안 뽑는 것이다.** 배운 게 없으면 0건이 정답이다. 억지로 뽑은
후보가 곧 노이즈가 되고, 그 노이즈는 reconciliation 대조 비용까지 늘린다.

## §3 무엇을 막을까

> **질문** — 형식이 완벽하고 사실이기까지 한데, 저장하면 안 되는 것.
> **답** — 안전 관련과 화면의 내용. 둘 다 코드가 막는다.

**§2와 다른 질문이다.** §2는 *"쓸모 있나"*를 묻고 §3은 *"허용되나"*를 묻는다. 승격 심사는
*"이게 반복되는 사실인가"*만 보기 때문에 아래 같은 후보는 **심사를 통과한다.**

```
kind: APP_FACT                  ← 형식 맞음
pkg:  com.kakao.talk            ← 키 맞음
text: "대화 목록 맨 위는 보통 '엄마'다"   ← 여러 실행에서 재현됨
```

### 규칙 A — 안전은 학습 대상이 아니다

`require_confirmation`이 붙었던 턴에서 나온 후보는 저장하지 않는다. **내용을 판정하지 않고
출처로 자른다** — 어떤 턴에 확인 카드가 떴는지는 우리가 이미 안다.

```kotlin
val tainted = episodes.filter { it.hadSafetyDecision }.map { it.turn }.toSet()
candidates.filter { it.sourceTurn !in tainted }
```

어기면 *"저번엔 확인 없이 됐다"*가 사실로 승격되어 안전 게이트를 무력화한다.

### 규칙 B — 구조는 저장하고 내용은 저장하지 않는다

판별 기준은 하나다.

> **다른 사람 폰에서도 참인가?** 참이면 구조, 그 사람에게만 참이면 내용.

| 후보 | 판정 | 이유 |
|---|---|---|
| "설정 → 알림 경로가 3단계다" | 구조 | 다른 폰에서도 참 |
| "첫 실행 시 튜토리얼이 뜬다" | 구조 | 앱의 동작 |
| "검색창에 최근 검색어가 남아 있다" | 구조 | 값을 적지 않음 |
| "최근 검색어에 '이직'이 있었다" | **내용** | 값을 적음 |
| "대화 목록 맨 위를 누르면 채팅방이 열린다" | 구조 | 이름 없음 |
| "대화 목록 맨 위는 보통 '엄마'다" | **내용** | 관계 |
| "인증번호는 6자리다" | 구조 | 형식은 앱의 성질 |
| "인증번호는 6자리이고 최근 값은 481920이었다" | **내용** | 정상 구조 사실에 관측값이 딸려 들어감 |

마지막 두 쌍이 선을 보여준다 — 같은 화면, 같은 요소인데 **값을 이름 붙여 적느냐 마느냐**다.

**세 번째 종류 — 관찰로 추론한 것.** `"이 사용자는 새벽에 쇼핑앱을 자주 연다"`는 화면 내용이
아니지만 행태 프로파일링이다. 역시 금지. 다만 선호는 출처에 따라 갈린다.

| 같은 내용, 다른 출처 | 저장 |
|---|---|
| 사용자가 **직접 말한** 선호 — "음악은 유튜브 뮤직으로 열어" | 허용 |
| 우리가 **관찰해서 추론한** 선호 | **금지** |

**사용자가 준 것은 받고, 훔쳐본 것은 받지 않는다.**

### 집행 — 네 겹, 등급이 다르다

| 등급 | 누가 | 무엇을 막나 | 성질 |
|---|---|---|---|
| **A 구조적** | 템플릿 | 두 칸뿐이라 값을 넣을 자리가 없음 | 어길 수 없음 |
| **B 코드** | Gateway | 숫자 4자리↑·전화번호·이메일·통화·**원문 대조** | 결정론적 |
| **C 모델** | reconciliation | 이름·관계·고유명사·행태 추론 | 비결정적 |
| **D 사람** | 목록 UI | 위 셋이 놓친 것 | 최종 |

**B층의 원문 대조가 핵심이다.** 후보의 토큰이 그 실행의 화면 텍스트에 *그대로* 있으면
의심한다 — 구조는 우리가 요약한 말이라 원문과 다르고, 내용은 화면에서 복사돼 와서 같다.

**완벽할 필요가 없다.** 오탐(구조인데 버림)은 기억 하나를 잃을 뿐이고 미탐(내용인데 통과)은
개인정보를 영구 저장한다. 그리고 **기억은 재관측이 가능하다** — 오늘 버려도 같은 앱을 다음에
쓰면 다시 뽑는다. 버리는 비용이 거의 0이므로 **애매하면 무조건 버린다.**

D층이 작동하는 이유: 새 기억은 `PENDING`에서 시작해 모델에게 가지 않는다. §7의 2회 승격
규칙이 **검역 기간을 겸한다.**

## §4 언제 쓸까

> **질문** — 기억을 언제 DB에 쓰는가.
> **답** — 실행이 **끝난 뒤 한 번**, 루프 밖에서. 실행 중에는 `episode`에 **기록만** 쌓는다.

**기록과 학습은 다르다.** 매 턴 `episode`에 행을 추가하는 것은 학습이 아니라 무슨 일이
있었는지 적어두는 것이다.

루프 안에서 쓰면 안 되는 이유 셋:

1. **결과를 모르는 시점의 추측이 저장된다** — 5턴째의 판단이 그 실행이 실패하면 틀린 교훈
2. **매 턴 지연이 는다** — 리플렉터는 LLM 호출이다
3. **실패한 실행의 잘못된 중간 판단이 남는다**

### 타임라인

```
[실행 시작 · 1회]
  목표 입력 → taskNote 읽기 → run 행 생성

[매 턴 · n회]
  스크린샷 → appNote 읽기 → 모델 판단 → 액션 실행 → episode 행 추가
            └ 읽기만 있고 기억 쓰기는 없다

[실행 종료 · 1회 · 루프 밖]
  run 갱신 → 리플렉터 → §3 필터 → reconciliation → memory 쓰기

[주기적 · 백그라운드]
  Janitor — 압축 · 감쇠 · 만료 · 상한 (§7)
```

### reconciliation — 쓰기의 필수 부품

같은 사실인데 리플렉터가 **매번 다른 문장을 쓴다.** 문자열 비교로는 영원히 같은 기억으로
안 묶이고, 그러면 §7의 카운터가 죽는다.

| 판정 | 처리 |
|---|---|
| `ADD` | 새 행 · `PENDING` · `score 1` |
| `NOOP` | 기존 행 `score + 1` — **여기서 승격이 일어난다** |
| `UPDATE` | 기존을 `RETIRED`로, `superseded_by`에 새 id |
| `DELETE` | 기존을 `RETIRED`로 |

**3단계로 미룰 수 없다.** 정리 기능이 아니라 승격 카운터의 전제다. 이것 없이 자동 추출을
켜면 같은 사실이 `score 1`짜리 중복으로 무한히 쌓이고 아무것도 승격되지 않는다.

## §5 어떻게 찾을까

> **질문** — 수백 건 중 지금 필요한 3건을 어떻게 고르는가.
> **답** — 5단계 파이프라인. 넓게 모으고, 하드 조건으로 자르고, 점수로 정렬하고, 예산으로
> 끊고, 기록한다.

**여기가 실패하면 앞의 넷이 무의미하다.** 잘 저장해놓고 잘못 꺼내면 소용이 없고, 더 나쁜 것은
엉뚱한 기억이 성능을 떨어뜨린다는 점이다(§9).

```
① 후보 수집   pkg exact match · keywords FTS5              ≈ 30건
② 하드 필터   ACTIVE · invalid_at NULL · 만료 전 ·
              sensitivity normal · precondition 충족        ≈ 7건
③ 랭킹        아래 점수식                                   정렬
④ 예산 컷     APP_FACT 2줄 + PITFALL 2줄 + RECIPE 1개       ≤ 5건
⑤ 기록        num_recalled++ · last_accessed · injection    부수효과
```

### 점수식

```
score = 0.40·relevance + 0.25·confidence + 0.15·recency + 0.20·version_match
```

| 항 | 값 |
|---|---|
| `relevance` | `APP_FACT`는 패키지 일치 `1.0` · `PITFALL`은 정규화 bm25 · `scope='vendor'`는 0.7 |
| `confidence` | `min(score,4)/4` × §7의 시간 감쇠 |
| `recency` | `exp(−ln2 · 미회상일수 / 반감기)` |
| **`version_match`** | 현재 버전 `1.0` · 구버전 `0.4` · 앱 무관 `1.0` |

**`version_match`가 우리 고유 항이다.** 가중치를 높게 준 이유는 이것이 **유일한 결정론적
신호**이기 때문 — 나머지 셋은 추정값이지만 `longVersionCode`는 사실이다.

> ⚠️ **이 숫자들은 시작값이지 정답이 아니다.** 근거 없이 정했다. §9의 측정으로 잡아야 하며,
> 그 전까지는 "이런 항들을 본다"는 **구조만 확정된 것**으로 읽어야 한다.

**인기순으로 정렬하면 안 된다.** 초판은 `ORDER BY num_recalled DESC`였는데 이것은 인기투표다
— 매일 여는 앱의 기억이 관련도와 무관하게 항상 이긴다. 게다가 `num_recalled`는 *주입된 횟수*를
셀 뿐이라 **50번 실패한 실행에 매번 들어간 기억도 50이 된다.**

### 키워드 매칭의 취약성 — 단계별 대책

`"휴지통에 넣어줘"`는 `'삭제'`에 걸리지 않는다. 이미 `CuClient.kt:207` 주석에 적힌 문제다.
**싼 것부터** 시도한다.

| | 방법 | 비용 | 언제 |
|---|---|---|---|
| 1 | **리플렉터가 동의어까지 `keywords`에 쓰게** | **0** — 이미 도는 호출 | 2단계 |
| 2 | 실행 시작에 목표를 정규 태그로 확장 | 텍스트 호출 실행당 1회 | 3단계 |
| 3 | 온디바이스 임베딩 (ONNX·MediaPipe) | APK +수십MB | 4단계 · 1·2로 안 되면 |

3번을 쓰더라도 **벡터 DB는 필요 없다** — 수백 건이면 BLOB을 읽어 코틀린 루프로 전수
코사인해도 즉시 끝난다. `APP_FACT`에는 적용하지 않는다(키가 정확한 식별자라 오히려 나빠진다).

### 저장 ≠ 주입

```
DB 전체                  120
  episode 제외        →   40
  ① 후보 수집         →   18
  ② 하드 필터         →    7
  ④ 예산 컷           →    3
실제 주입                  3
```

**DB에 담겼다는 것과 모델이 본다는 것은 전혀 다른 사건이다.**

## §6 어디에 붙일까

> **질문** — 고른 3줄을 요청의 어느 자리에 넣는가.
> **답** — `Task:` 아래 `Recent:`·`Note:` 두 블록과 `status.note`.
> **`system_prompt`에는 절대 넣지 않는다.**

**새로 깔 배관이 없다** — 주입 지점이 이미 코드에 있고 비어 있는 채로 대기 중이다.

### 세 경우 — 실측한 코드 기준

| | 작업 요청 | 기억 |
|---|---|---|
| **턴 1** (`userInput`) | `Task:` 줄 | `Recent:` 블록 + `Note:` 줄 — **`tNote`만** |
| **턴 2~n** (`putResult`) | **안 감** (서버 히스토리) | `status.note` — `tNote + appNote` |
| **승인 턴** | 안 감 | **안 감** ← 아래 |

```kotlin
// CuClient.kt:228 — 턴 1 조립
val text = if (note.isNullOrBlank()) "Task: $task" else "Task: $task\n\nNote: $note"

// CuClient.kt:262 — 턴 2~n
if (!note.isNullOrBlank()) status.put("note", note)
```

**승인 턴에는 기억이 안 붙는다.** `safety_acknowledgement` 형식이 워낙 까다로워
(`CuClient.kt:252`) 보수적으로 뺀 것이다. 위험 액션 확인 직후 한 턴뿐이라 영향은 작다.

### 코드 사실 정정 — 초안이 틀렸던 것 둘

1. **`taskNote`는 "실행 시작 1회"가 아니라 매 턴 전달된다.** 계산이 1회일 뿐이다.

```kotlin
val tNote = cu.taskNote(task)                      // :349  계산 1회
fun note() = listOfNotNull(tNote, exec.appNote())  // :350  매 턴 둘을 합침
                                    .joinToString(" ")
cu.putResult(..., note())                          // :407  매 턴 status.note 로
```

2. **턴 1에는 `appNote`가 안 붙는다.**

```kotlin
var resp = cu.cuCall(cu.userInput(task, png, tNote), null)   // :354 — tNote 만
```

사용자가 갤러리를 열어둔 채 "사진 지워줘"라고 하면 **첫 턴에 갤러리 `APP_FACT`가 안 붙는다.**
정작 그 화면을 보고 있는데도. 고치는 건 한 줄(`note()`를 넘김)이지만 **의도인지 누락인지
확인이 필요**하다(§부록 F).

### `Recent:` 블록 — 실행 단위 일화 주입 (신설)

초안은 *"일화는 주입하지 않는다"*라고 적었는데 **부정확했다.** 정확히는:

> **턴 단위 일화(`episode`)는 주입하지 않는다. 실행 단위 요약(`run`)은 주입한다.**

배제 근거였던 "20턴을 주입하면 예산이 터진다"는 `episode` 얘기지 `run` 얘기가 아니다.
`run`은 실행당 한 줄이다.

```
Task: 어제 쓴 일기 수정해줘

Recent:
  어제 18:04  "일기 써줘"     → 성공 · Samsung Notes · 12턴
  오늘 09:12  "알람 7시로"    → 성공 · 시계 · 4턴
  오늘 14:30  "사진 지워줘"   → 실패 · 갤러리 · 20턴

Note: Deletion flows are two-step: ...
```

이 세 줄이 있으면 *"어제 그거"*가 무엇인지, 어느 앱을 열어야 하는지 모델이 안다.

**비용이 거의 0인 이유 셋:**

| | |
|---|---|
| **LLM 호출 0** | `run` 헤더 조회 + `episode`의 `pkg` 최빈값. 리플렉터를 안 거친다 |
| **턴 1에만** | 목표 해석은 첫 턴에 끝난다. 이후엔 모델 컨텍스트에 남아 있다 |
| **`Note:` 예산과 무관** | 별도 블록이라 5줄 제한을 안 건드린다 |

실행 전체로 보면 `appNote` 2줄 × 20턴 = 40줄 상당, `Recent` 3줄 × 1턴 = 3줄. **약 4%다.**

**랭킹이 필요 없다.** 일화는 참·거짓이 없어 검증할 게 없다. `ORDER BY started_at DESC LIMIT 3`
이면 끝이고, `memory` 테이블에 안 들어간다 — **네 번째 `kind`가 아니라 별도 읽기 경로**다.

**한계.** `run.goal`은 사용자가 무엇을 시켰는지이지 결과물이 어디 있는지가 아니다. "어느
앱까지"만 도와주고 "그 일기가 어느 노트인지"는 모른다. 더 정확히 하려면 화면 내용을 담아야
하는데 그건 §3 규칙 B와 정면으로 부딪힌다.

### 왜 `system_prompt`는 안 되나

| 이유 | 내용 |
|---|---|
| **캐시** | 6,799 토큰이 매 실행 재사용된다. 기억이 섞이면 **매번 깨진다** |
| **희석** | 규칙이 늘수록 어느 것도 안 지킨다 |
| **안전** | 안전 규칙이 거기 있다. 자동 수정 대상이 되면 §3 규칙 A가 무너진다 |
| **추적** | 모델이 고친 프롬프트는 왜 그렇게 됐는지 되짚기 어렵다 |

LangChain 계열은 정반대로 `system prompt`를 절차 기억 저장소로 삼고 에이전트가 스스로 고쳐
쓰게 한다. 대화형 어시스턴트에는 성립하지만 **우리에겐 위 네 이유로 안 된다**(§부록 E).

### Memory Gateway — 유일한 출입구

DB를 만지는 객체를 하나로 좁힌다.

```
a11service.kt:247 (읽기·매 턴)   CuClient.kt:217 (읽기·실행 시작)
Reflector (쓰기·실행 종료)       MemoryListActivity (사람)   Janitor (정리)
                    │
                    ↓  전부 여기로
              MemoryGateway.kt      ← 예산 · 민감도 · 감사 · 가중치
                    ↓
              MemoryDao.kt          ← SQL 을 쓰는 유일한 파일
                    ↓
                memory.db
```

SQL이 흩어지면 예산 제한이나 §3의 필터를 어딘가에서 빠뜨리게 된다. **출입구가 하나면 거기만
지키면 된다.**

**판단 코어는 기억을 모른다** — `runAgent`·`CuClient`는 DB의 존재를 모르고, 함수
시그니처(`String?` 반환)도 그대로고, **API 표면은 0 증가**다.

## §7 강화와 소멸

> **질문** — 실행을 거듭하며 무엇을 믿게 되고 무엇을 버리는가.
> **답** — 축이 **둘**이다. **틀려짐**(아직 참인가)과 **없어짐**(언제 지우나).

대부분의 메모리 설계가 앞엣것만 다루고 뒤엣것을 빠뜨린다. **폰에서 뒤엣것이 없으면 그냥
버그다** — `episode`가 무한히 쌓이고 툼스톤이 영원히 남는다.

### 축 1 · 틀려짐 — 상태 기계

```
PENDING  ──score ≥ 2 또는 사람 승격──▶  ACTIVE  ──score ≤ 0 또는 사람 삭제──▶  RETIRED
(모델은 못 봄)                        (주입 대상)                       (invalid_at 기록)
```

| 사건 | 변화 | 근거 |
|---|---|---|
| 실패에서 추출 · 재관측 | 2회 → `ACTIVE` | 한 번은 우연일 수 있다 |
| 성공에서 추출 | 1회 → `ACTIVE` | 실제로 통한 경로다 |
| 사용자 발화 · 사람이 승격 | 즉시 `ACTIVE` | 명시적 판단 |
| **주입된 실행이 성공** | **`score + 1`** (상한 4) | 실전 검증 |
| 주입된 실행이 실패 | `score − 1` | 약한 신호로만 |

**성공 시 +1이 있어야 하는 이유** — 없으면 깎는 경로만 남아, 실전에서 50번 쓰여 50번 성공한
기억과 방금 겨우 승격된 기억의 `score`가 같아진다. 상한 4를 두어 매일 쓰는 앱의 기억이
무한정 부풀지 않게 한다.

**"2회"는 반드시 실행 간이다.** 리플렉터는 실행당 한 번만 돌므로 한 실행은 최대 +1만
기여한다. 한 실행 안의 반복 실패는 '모델이 루프에 빠진 것'이지 앱의 성질이 아니다.

### 무효화 — 다섯 겹

| | 겹 | 시점 | 하는 일 |
|---|---|---|---|
| 1 | 좌표 미저장 | 저장 시점 | 애초에 잘 안 썩는 것만 저장 |
| 2 | precondition 검증 | RECIPE 사용 직전 | 조건 안 맞으면 §5 ②단계에서 탈락 |
| 3 | 실패 시 강등 | 주입된 실행이 실패 | `score − 1` |
| **4** | **앱 버전 태깅** | `longVersionCode` 변경 | **랭킹 감점 + 사용자 확인 요청** |
| 5 | 사용자 삭제 | 사람이 언제든 | 실무적으로 가장 확실 |

**4번이 차별점이다.** 다른 시스템은 "이 사실이 언제 무효가 됐나"를 LLM 추론이나 시간 규칙으로
힘겹게 판정한다. 우리는 `longVersionCode`가 바뀌는 것을 **결정론적으로** 안다. UI 변경이
staleness의 주원인인데 그 사건을 직접 관측하는 것이고, **폰 안에 있어야만 가능하다.**

다만 **즉시 강등하지 않는다** — 마이너 업데이트는 대개 UI를 안 바꾸는데 매번 전부 날리게
된다. `ACTIVE`를 유지하되 `version_match`를 감점하고 목록 UI에 *"갤러리가 업데이트됐습니다 ·
확인 필요 3건"* 배지를 띄운다.

> **credit assignment 한계** — 실행이 실패했을 때 그게 주입된 기억 탓인지 **원리적으로 알 수
> 없다.** `injection` 테이블로 관여 여부까지만 안다. 그래서 3번은 약한 신호로만 쓰고,
> **실질적 무효화는 §8에서 일어난다.**

### 축 2 · 없어짐 — 보존 정책

| 대상 | 보존 | 이후 |
|---|---|---|
| `episode` 턴 상세 | **30일** | run 단위 요약으로 **압축** 후 턴 행 삭제 |
| `run` 요약 | 1년 | 삭제 — `episode`·`injection`은 `CASCADE` |
| `PENDING` | **90일 무변동** | 삭제. score가 오르면 시계 리셋 |
| `RETIRED` | 180일 | 삭제. `superseded_by`로 참조되면 유지 |
| `ACTIVE` | 무기한 | **자동 삭제 없음.** 감쇠와 상한만 |

**용량 상한** — `memory` 총 500건. 초과하면 점수 최하위부터 `PENDING`으로 **강등한다(삭제
아님)** — 사람이 볼 기회를 남긴다. `pinned=1`은 제외.

**압축** — 오래된 `episode`를 지우지 말고 요약한다.

```
before  episode 20행 (턴별 액션·의도·결과 전문)
after   run.summary = "갤러리 삭제 흐름 시도. 확인 다이얼로그에서 2회 실패 후
                       17턴에 완료. 기억 #12 관여."
        episode 20행 삭제 · injection 은 남긴다
```

**감쇠** — 사건이 아니라 시간에도 반응하게.

```
confidence(t) = base_score × exp( −ln2 × 미회상_일수 / 반감기 )
```

**반감기는 `kind`마다 다르다** — 부패 속도가 전혀 다르기 때문이다.

| `kind` | 부패 요인 | 속도 |
|---|---|---|
| `PITFALL` | 거의 없음 | **느림** — 앱 무관한 일반 패턴 |
| `APP_FACT` | 앱 버전 변경 | **빠름** — UI가 바뀌면 즉시 틀려짐 |
| `RECIPE` | 앱 버전 + 흐름 변경 | **가장 빠름** — 다단계라 한 곳만 깨져도 전체가 틀림 |

감쇠는 `ACTIVE`를 자동 강등시키지 않는다 — §5의 랭킹과 상한 정리에만 쓴다. **구체적 반감기
값은 미정**(§부록 F).

## §8 사람의 개입

> **질문** — 사람은 무엇을 할 수 있고, 무엇을 반드시 해야 하는가.
> **답** — 목록 편집·자연어 피드백·삭제 셋을 할 수 있다. **반드시 해야 하는 것은 없다.**

사람이 아무것도 하지 않아도 자동 루프만으로 굴러가야 한다. 사람 손을 필수로 만들면 자동화
에이전트라는 취지에 반한다.

**그런데 실질적 무효화는 여기서 일어난다.** §7의 카운터는 무작위 노이즈만 막고, **모델의
체계적 편향은 사람만 막는다** — 같은 모델이 같은 편향을 가지면 서로 다른 실행에서도 똑같이
틀리고, 카운터는 그걸 오히려 승격시킨다. 그래서 목록 UI는 편의 기능이 아니라 **아키텍처의
일부**다.

| | 창구 | 무엇을 하나 | 결과 |
|---|---|---|---|
| 1 | 기억 목록 UI | 후보 승격·수정·삭제. 비동기 | `pinned=1` |
| 2 | 자연어 피드백 | 실행 결과 아래 한 줄. 비워도 됨 | 즉시 `ACTIVE` · `pinned=1` |
| 3 | 삭제 | 개별 · 앱 단위 · 전체 초기화 | 행 제거 |

**왜 창구 2가 반드시 필요한가** — `"음악은 유튜브 뮤직으로 열어"`는 **로그에 성공으로
찍힌다.** 작업이 성공해도 사용자는 불만족일 수 있고, 로그는 그 차이를 원리적으로 볼 수 없다.

### 삭제권 — 협상 대상이 아니다

- **개별 삭제** · **앱 단위**("갤러리에 대해 배운 것 전부") · **전체 초기화**(되돌릴 수 없음을
  명시하고 확인)
- **전부 볼 수 있을 것** — 목록에 숨겨진 항목이 있으면 안 된다

기억이 사용자의 화면에서 파생되므로 무엇이 저장됐는지 보고 지울 수 있어야 한다. §3이 저장
시점의 방어라면 이것은 사후 방어다. 그리고 **자동 쓰기(2단계)가 시작되기 전에 있어야 한다** —
순서가 반대면 그사이 쌓인 것에 사용자가 손쓸 방법이 없다.

### 목록에 무엇을 보여줘야 하나

사람이 판단하려면 **근거를 봐야 한다.** 문장만 덜렁 있으면 맞는지 틀린지 알 수 없다.

| 항목 | 왜 |
|---|---|
| 기억 문장 | — |
| **어느 실행에서 나왔나** | `source_run_id` → "실행 #37에서 배움 · 그때 뭐 했는지 보기" |
| 상태 · 점수 | 얼마나 검증됐나 |
| 버전 경고 배지 | §7 4번 — 앱이 업데이트됐다 |
| 대체 관계 | `superseded_by` — "v5 업데이트 때 이걸로 바뀜" |

### 사용자 설정과 측정용 파라미터는 다른 것이다

**랭킹 가중치를 사용자에게 노출하지 않는다.** `0.40·relevance`가 무슨 뜻인지 알 수 있는
사용자는 없고, 튜닝을 시키는 것은 설계 실패를 떠넘기는 것이다.

| | 사용자 설정 | 측정용 파라미터 |
|---|---|---|
| 무엇 | 기억 켜기/끄기 · 목록 · 초기화 | 가중치 · 반감기 · 상한 |
| 어디 | 설정 화면 | **소켓 명령 + 디버그 빌드 전용** |
| 수명 | 영구 | **측정 기간 한정 — 끝나면 상수로 굳힘** |

8080 소켓 서버(`a11service.startServer`)가 이미 `SHOT`/`TAP`/`RUN`을 받고 `tools/bench_*.py`가
붙어 있다. `SET rank.relevance 0.40` 한 줄이면 **폰을 손대지 않고 PC 스크립트로 스윕**할 수
있다.

## §9 효과가 있나

> **질문** — 이 시스템이 실제로 도움이 되는지 어떻게 아는가.
> **답** — 같은 작업 세트를 기억 `on`/`off`로 교차 실행 + **들어오면 안 되는 기억**을
> 라벨링해 노이즈를 직접 잰다.

이 축이 없으면 안 되는 이유 둘 — **첫째, 기억이 성능을 떨어뜨린 사례가 이미 셋 관측됐다.
둘째, 이 설계의 숫자가 전부 근거 없다.**

| 출처 | 관측 |
|---|---|
| **Agent S → Agent S3** (Simular) | 지식 베이스를 통째로 삭제하고 OSWorld **20.6% → 69.9%** |
| **Co-Learning** (HumemAI) | 초반엔 개선, 어려운 후반엔 **부정적 효과** |
| **Mobile-Agent-v2** (X-PLUG) | memory unit을 제거해도 **−2.2점**. 세 컴포넌트 중 최하 |

### 지표 다섯

| 관점 | 지표 | 측정 방법 |
|---|---|---|
| 과제 성능 | 성공률 · **평균 턴 수** | 작업 10~15개를 `on`/`off` 교차 실행 |
| **검색 품질** | `precision@5` · **forbidden 주입률** | 질의별로 들어와야 할 기억과 **들어오면 안 되는 기억**을 라벨링 |
| **staleness** | 구버전 기억 주입률 | 주입된 기억 중 `pkg_version ≠ 현재`인 비율 — **결정론적** |
| 충돌 | 모순 동시 주입률 | 같은 대상에 다른 값을 말하는 기억이 함께 나간 횟수 |
| 비용 | 주입 토큰 · 리플렉터 호출 | 예산 5줄이 지켜지는지 · 학습이 실행당 1회인지 |

**`forbidden_memories`가 핵심이다.** 성공률만 보면 노이즈가 늘어도 안 보인다 — 쓸모없는 2줄이
더 들어가도 과제는 성공할 수 있다. 그러나 그것이 쌓이면 위 세 사례처럼 어느 순간 꺾인다.

### 어디에 집중할지도 측정이 정했다 — 다만 지표를 나눠 봐야 한다

| 기억이 하는 일 | 성공률 효과 | 함의 |
|---|---|---|
| **모델이 모르는 지식을 준다** (`APP_FACT`)<br>AppAgent 앱별 문서 48.9% → 73.3% | **+24.4** | 여기 집중 |
| 유사 작업을 회상한다 (`RECIPE`)<br>Synapse · Mind2Web | +1.4 | 아래 주의 |

> ⚠️ **`RECIPE`의 +1.4를 "근거가 약하다"로 읽으면 안 된다.** 그것은 *성공률* 지표이고, 절차
> 재사용의 이득은 주로 **턴 수 절감**에 나타난다. 이 프로젝트에서 벽시계의 ~85%가 API
> 왕복이므로 **속도 = 총 턴 수**다. 20턴이 12턴이 되면 성공률이 그대로여도 큰 이득이다.
> 정확히는 *"그 효과를 재는 숫자가 아직 없다"*이며, 위 표의 출처는 웹 에이전트의 성공률이다.

**`Recent:` 블록은 분산이 크다.** `APP_FACT`는 그 앱에 있는 동안 항상 조금씩 유용하지만,
`Recent`는 *"어제 그거"*면 매우 크고 *"유튜브 열어줘"*면 완전히 무용하다. **평균 효과로
판단하면 안 되고**, 측정 세트에 "이전 실행을 참조하는 작업"을 따로 몇 개 넣어 **그 그룹만
따로 봐야** 한다.

**측정 세트는 1단계와 함께 만든다.**

## 부록 A · 스키마

표 4개, 전부 평평하다. SQLite에 `BOOLEAN`이 없어 `pinned`은 `0`/`1`, 시각은 전부
`INTEGER`(epoch millis), 배열이 없어 `keywords`는 쉼표 구분 문자열이다.

```sql
CREATE TABLE run (
  id           TEXT PRIMARY KEY,
  goal         TEXT NOT NULL,
  model        TEXT NOT NULL,
  thinking     TEXT NOT NULL,
  max_turns    INTEGER NOT NULL,
  outcome      TEXT,               -- success|fail|aborted|error
  turns_used   INTEGER,
  started_at   INTEGER NOT NULL,
  ended_at     INTEGER,
  summary      TEXT,               -- 압축 결과 (§7)
  compacted_at INTEGER
);

CREATE TABLE episode (             -- 일화 · 턴 단위 · 주입하지 않는다
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  run_id      TEXT NOT NULL REFERENCES run(id) ON DELETE CASCADE,
  turn        INTEGER NOT NULL,
  pkg         TEXT,
  pkg_version INTEGER,             -- longVersionCode ★ §7
  action      TEXT,                -- 좌표는 담지 않는다
  intent      TEXT,
  result      TEXT,                -- ok|error|blocked
  had_safety  INTEGER NOT NULL DEFAULT 0,   -- §3 규칙 A
  note        TEXT,                -- 그 턴에 주입된 메모
  created_at  INTEGER NOT NULL
);

CREATE TABLE memory (              -- 의미 · 절차 · 주입된다
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  -- 내용
  kind          TEXT NOT NULL,     -- APP_FACT|PITFALL|RECIPE
  text          TEXT NOT NULL,     -- 주입 문장 (영문 권장)
  steps         TEXT,              -- RECIPE 전용 · JSON 배열
  precondition  TEXT,              -- RECIPE 전용
  observed_turns INTEGER,          -- RECIPE 전용 · 턴 절감 측정 기준
  -- 검색 키
  pkg           TEXT,
  keywords      TEXT,              -- 동의어 포함
  scope         TEXT NOT NULL DEFAULT 'pkg',   -- pkg|vendor|system
  embedding     BLOB,              -- 4단계까지 NULL
  -- 신뢰
  state         TEXT NOT NULL DEFAULT 'PENDING',
  score         INTEGER NOT NULL DEFAULT 1,
  pinned        INTEGER NOT NULL DEFAULT 0,
  source        TEXT NOT NULL,     -- reflector|user_ui|user_feedback
  source_run_id TEXT REFERENCES run(id),      -- 근거 (§8)
  sensitivity   TEXT NOT NULL DEFAULT 'normal',
  -- 수명
  pkg_version   INTEGER,
  time_added    INTEGER NOT NULL,
  last_accessed INTEGER,
  num_recalled  INTEGER NOT NULL DEFAULT 0,
  invalid_at    INTEGER,
  expires_at    INTEGER,
  superseded_by INTEGER REFERENCES memory(id)
);

CREATE TABLE injection (           -- credit assignment
  run_id    TEXT NOT NULL REFERENCES run(id) ON DELETE CASCADE,
  memory_id INTEGER NOT NULL REFERENCES memory(id),
  PRIMARY KEY (run_id, memory_id)
);

CREATE INDEX idx_mem_lookup ON memory(pkg, state, kind);
CREATE INDEX idx_mem_gc     ON memory(state, last_accessed);
CREATE INDEX idx_ep_run     ON episode(run_id, turn);

CREATE VIRTUAL TABLE memory_fts USING fts5(
  text, keywords, content='memory', content_rowid='id'
);
```

`memory` 테이블의 칸은 **네 덩어리**다 — 내용(주입되는 것) · 검색 키(§5) · 신뢰(§7) ·
수명(§7). **수명 칸이 가장 많다.** 무효화가 제일 어려운 문제라는 게 스키마에 그대로 드러난다.

실제로 모델에 실려 가는 것은 `text` 한 줄(또는 `RECIPE`의 `steps`)뿐이고, 나머지 열일곱 칸은
전부 **그 한 줄을 언제 꺼내고 언제 버릴지**를 정하기 위한 것이다.

### `APP_FACT` 한 행 예시

```
id            12
kind          "APP_FACT"
text          "Samsung Gallery: tapping the trash icon opens a
               second confirmation dialog that must also be confirmed."
pkg           "com.sec.android.gallery3d"
pkg_version   1400300
keywords      "delete,remove,trash,휴지통,삭제,지우"
scope         "pkg"
state         "ACTIVE"      score 2      pinned 0
source        "reflector"   source_run_id "a3f9c1…"
sensitivity   "normal"
last_accessed 1757894000000  num_recalled 3
invalid_at    null           superseded_by null
```

### `RECIPE` 한 행 예시

```
kind           "RECIPE"
steps          ["open YouTube Music (not YouTube)",
                "tap the search tab",
                "type the song name",
                "tap the first result"]
precondition   "홈 화면 또는 앱 서랍"
observed_turns 6
keywords       "음악,노래,재생,play,music"
```

**`steps`는 서술이지 좌표가 아니다** — 모델이 "검색 탭"을 매번 화면에서 찾는다.
`observed_turns`가 있어야 이 레시피가 실제로 턴을 줄였는지 잴 수 있고, 안 줄이면 폐기 근거가
된다.

## 부록 C · 세 기억의 저장 메커니즘

세 개가 **저장 시점 · 검증 절차 · 저장 형태**가 전부 다르다.

| | 일화 | 의미 | 절차 |
|---|---|---|---|
| 테이블 | `episode` | `memory` | `memory` |
| `kind` | — | `APP_FACT`·`PITFALL` | `RECIPE` |
| 누가 쓰나 | 앱 | 리플렉터 | 리플렉터 |
| 언제 | **실행 중 매 턴** | 실행 후 1회 | 실행 후 1회 |
| 조건 | **없음 — 무조건** | 배운 게 있으면 | **성공했을 때만** |
| 검증 | 없음 | reconciliation + score | score + **precondition** |
| 모델에 주입 | 턴 단위 ✗ / **실행 요약 ✓** | ✓ | ✓ (조건부) |
| 단위 | 1턴 → 1행 | 1관찰 → 1문장 | **N턴 → 1레시피** |

### 일화 — 판단 없이 기록만

가장 단순하다. 아무 검증이 없다. **기록이지 학습이 아니라서** "무슨 일이 있었나"에 참·거짓
판정이 필요 없다.

턴 단위(`episode`)는 주입하지 않는다 — 20턴을 넣으면 5줄 예산이 즉시 터지고, 지난 실행의
삽질은 지금 도움이 안 된다. **다만 실행 단위 요약(`run`)은 주입한다**(§6 `Recent:`).

### 의미 — 검증이 붙는다

```
episode 전체 → 리플렉터(템플릿) → §3 필터 → reconciliation
             → PENDING(score 1) → 재관측 → score 2 → ACTIVE
```

핵심은 `reconciliation`이다. 같은 사실을 리플렉터가 매번 다른 문장으로 쓰기 때문에, 문자열
비교로는 영원히 같은 기억으로 안 묶이고 카운터가 죽는다.

### 절차 — 압축이 붙는다

여기가 가장 어렵다. 앞의 둘과 근본적으로 다르다.

> 의미 기억은 **한 관찰 → 한 문장**인데, 절차 기억은 **N턴 → 한 레시피**다.

```
성공한 실행의 episode 20행
    ↓  어느 턴이 본질이고 어느 턴이 삽질인가?   ← 여기가 어려움
steps 배열로 압축 → precondition 붙이기 → ACTIVE (성공 1회면 승격)
```

**성공에도 삽질이 섞여 있다.** 20턴 성공 = 본질 12턴 + 헤맨 8턴일 수 있다. 의미 기억은 "이
사실이 참인가" 하나만 보면 되는데, 절차는 **"이 순서가 최단인가"**까지 봐야 한다.

**실패한 실행에서는 절대 안 뽑는다.** 실패한 경로를 절차로 저장하면 그건 함정을 레시피라고
부르는 것이고, 그건 `PITFALL`로 가야 한다.

### 층이 하나씩 늘어난다

```
일화   기록만              →  판단이 필요 없음
의미   기록 + 판정          →  "참인가"
절차   기록 + 판정 + 압축   →  "참인가" + "최단인가"
```

구현 순서(0단계 → 2단계 → 4단계)가 이 순서를 따르는 이유다. 부패 속도도 같은 순서다.

### 용어 — `procedural`을 설계 어휘로 쓰지 않는다

인지심리학의 절차 기억은 **"말로 옮길 수 없는 수행 능력"**으로 정의된다. 그 정의를 엄격히
적용하면 `RECIPE`는 문장으로 적혀 있으므로 의미 기억이고, 진짜 절차 기억은 모델 가중치와 앱
코드가 된다(CoALA의 정의가 이것이다).

**그러나 AI 에이전트 실무 문헌(LangChain·Mem0·IBM 등)에서 procedural memory는 "성공했던 행동
궤적이나 루틴을 저장해 매번 재추론하지 않게 하는 것"을 뜻하고, 그것이 정확히 우리
`RECIPE`다.** 초안이 "절차 기억은 DB 밖"이라고 쓴 것은 오해를 불렀다 — 우리는 그것을 만들고
있고, 다만 4단계로 미뤄뒀다.

**살아남는 쟁점은 정의가 아니라 인코딩이다.**

| 궤적을 이렇게 저장하면 | |
|---|---|
| `click(412,830) → click(500,900)` | ✗ **매크로.** UI 한 번 바뀌면 전부 깨짐 |
| `POST /api/cart → POST /api/checkout` | ✓ 식별자가 안정적 — 웹·API 에이전트는 이게 됨 |
| **"YouTube Music을 열고 → 검색 탭 → 곡명 입력"** | ✓ 모델이 매 단계 화면을 봄 ← **우리 방식** |

브라우저·API 에이전트가 궤적 재생을 안전하게 하는 건 다음에도 그 식별자가 그대로 있기
때문이다. 우리는 픽셀을 누르는 GUI 에이전트라 그 전제가 없다 — AppAgent가 좌표를 저장했다가
앱 업데이트에 전부 무효화된 것이 그 사례다.

혼란을 줄이기 위해 **이 문서는 `procedural`이라는 단어를 쓰지 않고 `RECIPE`로만 부른다.**

### 업계는 삼분법을 쓰지 않는다

| | 나누는 축 | 실제 구분 |
|---|---|---|
| LangChain | 내용 종류 | semantic·episodic·procedural — 삼분법을 쓰는 거의 유일한 곳 |
| Letta | 거주지 | core(항상 컨텍스트)·recall·archival — OS 가상메모리 은유 |
| Mem0 | 파이프라인 | extract → consolidate → retrieve |
| Zep | 시간 유효성 | 모든 노드·간선에 validity window |
| **우리** | 셋 다 | `kind`(검색 키) × `state`(믿을 만한가) × `pkg_version`(아직 유효한가) |

**축은 "무엇을 관리해야 하는가"에 따라 고르는 것이다.** Zep은 모순되는 사실이 문제라 시간
축을, Letta는 컨텍스트 예산이 문제라 거주지 축을 골랐다. 우리 문제는 *패키지별 UI 지식이 앱
업데이트로 썩는 것*이라 위 세 축이 됐다.

## 부록 D · 실행 계획

| 단계 | | 무엇 | 왜 이 순서 |
|---|---|---|---|
| **0** | **구조화 로깅** | `run_history.txt` 평문 → 턴별 JSONL + `injection` | 단독으로도 디버깅 가치 |
| 1 | **저장소 + 목록 UI** | 하드코딩 맵 → 파일 읽기. 사람이 채우고 **지울 수 있다**. `Recent:` 블록. 측정 세트 | 상한을 먼저 재고 자동화 |
| 2 | **자동 추출** | SQLite 전환 + 리플렉터 + reconciliation + 승격 + 자연어 피드백 + §3 필터 | reconciliation은 분리 불가 |
| 3 | **생애주기** | 보존·압축·감쇠·상한 + 버전 태깅 + 목표 태그 확장 | 쌓여야 필요성이 보임 |
| 4 | **RECIPE · 벡터** | `steps` 재사용 + precondition · 필요가 측정되면 임베딩 | 정체성 경계에 가장 가까움 |

**0단계가 없으면 아무것도 시작되지 않는다.** §2의 리플렉터가 읽을 재료가 `episode`인데 그게
없다. §9의 숫자들도 전부 이 로그가 쌓여야 정할 수 있다 — **0단계는 구현이자 측정 준비다.**
게다가 같은 데이터가 곧 파인튜닝·오프라인 RL 데이터셋의 형태다.

**1단계는 JSON 파일로 시작해도 된다.** SQLite가 필요해지는 이유는 *자동 쓰기* 때문이다(§1).
사람만 편집하는 1단계에는 그 두 문제가 없다.

**삭제 UI는 1단계다.** 자동으로 쌓기 *전에* 지울 수단이 있어야 한다.

**`RECIPE`를 4단계에 둔 이유는 "근거가 약해서"가 아니다** — §9에서 정정했듯 그 효과를 재는
숫자가 아직 없을 뿐이다. 뒤로 둔 실제 이유는 셋이다: ⑴ 정체성 경계(매크로)에 가장 가깝고
⑵ precondition 검증이 선행돼야 하고 ⑶ `APP_FACT`가 먼저 효과가 크다. **턴 수 관점에서 보면
4단계가 너무 뒤일 수 있다** — 재검토 여지를 남긴다.
